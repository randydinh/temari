## Decision

**Live pilot update:** Nature Detective was delivered and independently verified
as the external product test case. The installed standalone Temari Codex
builder/reviewer bridge and task continuity ran. Codex app chats performed the
planning, implementation-stage dispatch and verification-stage handoffs; direct
Xcode/XCTest supplied product acceptance. This does not establish Archon-owned
native orchestration, full canonical feature delivery or cross-provider/host
consistency. The user clarified that those were the pilot's primary purpose, so
the broader evaluation remains open. Continue with the existing Archon route and
a bounded proof of the missing execution boundary, using the delivered feature's
baseline and acceptance evidence; do not count the app result as pilot completion.

Keep Temari's provider-neutral control plane. First make the requested outcome,
admitted workflow policy and completion boundary consistent across entry points.
Preserve Codex as an execution adapter and Archon as the preferred managed
harness. Prove one useful product journey before broadening the execution matrix.
Moving model calls into Archon alone would not establish portability or repeatable
outcomes, and provider independence does not require replacing working Codex agents.

The user's target is compatibility **and consistent, repeatable workflows and
outcomes**. The current core supports that target. The dashboard supplies bounded
Codex candidate production, while the packaged feature entry supplies a different,
stricter admitted journey. Those are different operations with different completion
boundaries. Their coexistence is not proof that the canonical workflow was bypassed;
presenting them as equivalent ways to complete a feature would be misleading.
Existing isolation, evidence and recovery mechanics are useful assets to retain.

Repeatability should mean the same admitted obligations, ownership boundaries,
stage gates, product acceptance checks and evidence rules. Different models can
produce different valid plans and code. Identical generated bytes are not a
reasonable general acceptance condition. A model's PASS claim cannot replace
independent product checks or procedural workflow verification.

Portability should be stated per supported route and capability set. A host that
lacks a required capability may correctly block that route. A documented weaker
route is a separate choice, not an equivalent successful execution of the original
obligations. Identical acceptance rules also do not establish equal success rates
across models; outcome quality requires repeated product-level observation.

## Three existing journeys

| Entry or operation | What it currently admits | Completion boundary |
| --- | --- | --- |
| [Packaged Temari engineering entry](../../packages/workflow-runtime/public/bin/public-entry.mjs) | Pinned lightweight or feature policy. The [feature profile](../../packages/workflow-runtime/public/policy.json) requires delegated architecture/build/review proof, revision-bound evidence and PR delivery. | Canonical stage evidence and route-specific closeout. The feature profile cannot be silently changed into local-only delivery. |
| [Dashboard planner and implementation](../../tools/dashboard-controller.mts) | A configured plan, or a goal fitted into 2–4 fixed independent ownership slots, fixed checks and a required separate reviewer. | An isolated, checked and reviewed candidate for coordinator assessment. It does not automatically apply or publish the candidate or perform feature closeout. |
| [Archon-backed task verification](../../docs/task-dashboard.md) | Configured native workflows with exact native identity and stage evidence for their declared checks. | Native execution and retained check evidence; native success alone is not feature acceptance. |

The public feature path already has [host proof collection](../../packages/workflow-runtime/host/feature-proof.mjs)
and [Codex worker observation](../../packages/workflow-runtime/host/local-worker.mjs).
The migration should reuse their applicable contracts rather than invent another
capability framework. Their existing proof is bound to a specific invocation and
candidate; a dashboard worker report cannot be relabeled as that proof after the fact.

The dashboard planner is deliberately bounded: `parseProposal` rejects dependent
assignments and `promptFor` requires work outside the configured slots/checks to
block. This is useful parallel candidate production, but it does not implement
general product decomposition. Correctly fitting a user's complete goal to those
checks remains a semantic responsibility; passing fixed checks alone cannot prove
that every requested behavior was covered.

Broader autonomous product orchestration is a separate gap. The
[program ownership decision](../../docs/decisions/2026-09-30-temari-program-ownership.md)
and [capability index](../../docs/pstack-audit/index.md) keep the typed program route
at planning-only admission. Existing bounded engineering can be used to build
successive product increments, but the current dashboard is not proof of automatic
dependent planning, execution and recovery across an entire product program.

## Intended ownership

The [architecture](../../docs/architecture.md#responsibility-split) separates
semantic decisions, mechanical control, host facilities and native execution.
The [accepted harness decision](../../docs/decisions/2026-09-22-archon-harness.md)
allows injected and configured harnesses ahead of managed Archon. The
[September 30 approved direction](../../docs/system-roles-and-responsibilities.md)
prefers a Temari-managed task experience on Archon.

| Boundary | Owner | What switching providers must preserve |
| --- | --- | --- |
| Goal, plan, replanning and acceptance | Temari coordinator, with Poteto supplying engineering method | User constraints and explicit delegation, review, evidence and delivery obligations |
| Stage order and gates | Canonical workflow engine | `investigate → plan → build → review → verify → deliver`; early nonpassing stages retain evidence and stop progression |
| Durable task/child identity and evidence | Workflow runtime | Immutable bindings, bounded concurrency, leases, fencing, retained results and recovery uncertainty |
| Model and tool execution | Selected host/model adapter | Admitted tools, typed briefs/results, execution identity and refusal of unsupported capabilities |
| Native run control | Selected harness | Exact-run start/status/resume/cancel where supported, independently verifiable identity and native-to-Temari evidence links |
| Source evidence | Content Registrar or another admitted knowledge provider | Pinned source identity, citations and explicit gaps |

The host is the execution environment and its available tools; the model provider
supplies inference; the harness controls native runs. Supporting several model
transports does not prove several complete engineering hosts.

The dashboard's capability report honestly marks subagents, model diversity,
worktree isolation, durable delivery and forge unavailable, and describes its
parallelism proof as unproven until actual process evidence exists. Preserve that
honesty. The public feature bridge can independently admit subprocess worker proof
as `subagents`; a vendor's native subagent API is not the only possible mechanism.
Reuse and verify the applicable proof contract instead of copying capability flags
between unrelated runs.

There is no evidence here that the dashboard falsely marks a feature DONE. The
[retained live coding proof](../task-continuity/dashboard-autonomy-2026-10-01.md)
ends at NEEDS_REVIEW and preserves the unchanged source checkout. The concern is
portable policy and complete workflow equivalence, not absence of useful coding.

## Architecture choices

| Option | Benefit | Remaining limitation |
| --- | --- | --- |
| Keep Codex as the first admitted execution adapter | Retains proven local candidate production and permits immediate product use within its scope | A second provider remains unproven; this is a legitimate initial implementation of a portable contract |
| Put the current Codex scripts under Archon unchanged | Can improve native run visibility and control | Still Codex-specific; policy and completion differences remain unless deliberately integrated |
| Align route policy, retain execution adapters, then prove the managed Archon journey | Preserves existing mechanics while making equivalent requests and outcomes testable | Requires a bounded integration and a real product proof; a broader compatibility matrix can follow |

Choose the third option while retaining Codex as the initial adapter. Prefer
Archon for the managed dashboard run experience because that is the approved
product direction. Treat that as an execution and UX choice separate from the
provider-neutral policy requirement. Exact migration effort requires a first
integration slice; the current evidence does not justify a rewrite or a mandatory
second harness implementation before useful product work.

## Recommended implementation sequence

1. **Choose one useful product increment and its actual finish condition.** Use a
   small change in a repository outside Temari, with concrete requirements and
   acceptance checks. State whether the outcome is a reviewed local candidate or
   a delivered feature. Preserve the selected route's delivery obligations; the
   existing public feature profile requires a PR. Do not postpone all product use
   until every host has been implemented.
2. **Make equivalent entry points use one admitted policy.** Reuse public routing,
   method and proof contracts where they apply. Keep the full request, plan and
   task record consistent about review, evidence and delivery. Connect the dashboard
   to the selected journey rather than creating another workflow policy there.
   A candidate-only tool can remain a bounded operation inside that journey.
3. **Prove the preferred managed execution using existing Codex workers.** Use
   Archon for native run control in the chosen dashboard journey, with one owner
   for each retry/cancel unit. Preserve runtime task identity, evidence and fencing.
   The model-free `startCanonical` bridge is a starting pattern, not a completed
   model-driven engineering route. Extend only the integration needed for the
   chosen product increment; preserve independently admitted direct execution
   until replacement parity is demonstrated.
4. **Add a second provider against that same contract.** Extract the smallest
   necessary planning/worker adapter seam while retaining common isolation,
   integration and checks. Reuse `ModelTransport` only where its context and tool
   contract fits; text completion alone is insufficient for coding. Prove one
   alternative worker backend with the same harness and capability obligations.
   Test an alternate harness as a separate compatibility dimension when needed.

For the first useful increment, require one retained task, a goal-to-check mapping,
scoped workers when warranted, exact-candidate review, recovery after listener
restart, and the selected route's real completion result. That supplies a concrete
stop condition for platform work. Subsequent Temari improvements should be driven
by failures or friction observed while building that product.

This sequence adds compatibility at existing seams. It does not require a new
dashboard, another task store, a new orchestration agent, support for every vendor,
or a general swarm scheduler before building useful software.

## Conformance and outcome gate

First compare equivalent entry points under one supported execution choice. Then
hold the harness fixed while comparing providers; hold the provider fixed when
evaluating a different harness. This isolates the cause of a difference and avoids
requiring every combination before the first product is usable.

Use the same clean product fixture, initial revision, user goal, mandatory
acceptance checks and declared policy across supported combinations. Retain the
proposed plan and all subsequent evidence for each new run. Exercise both frozen
plan replay (mechanical repeatability) and newly generated proposals (model quality).
Record provider/adapter/model settings, resolved executor version, policy/brief
digests, candidate identity and tool configuration without credentials.

| Scenario | Required observation across supported combinations |
| --- | --- |
| Successful product change | A requirement-specific check reproduces the missing behavior before the change and passes afterward; existing regression checks remain passing; independent review inspects the exact integrated candidate; all evidence required by the selected route is retained |
| Missing required capability | Work blocks before dispatch; no fabricated agent, automatic downgrade or completion receipt |
| Worker failure or unowned edit | Successful sibling retained; invalid patch rejected; review and completion cannot silently skip required work |
| Listener restart or uncertain dispatch | Same task and exact run remain discoverable; accepted work is not replayed; unknown ownership remains visible until reconciled |
| Cancel during coding/checks/review | The selected executor's actual termination is observed; successful completion racing cancellation is recorded accurately |
| Evidence/candidate drift | Changed goal, policy, source, integration commit or evidence bytes invalidate admission or acceptance |
| Provider/harness change | Explicit new run and execution identity; an old run cannot resume under a different bound harness/version |
| Final acceptance | Product correctness and procedural workflow conformance are both required; worker PASS or native SUCCEEDED alone cannot close the task |

Run the successful case multiple times per admitted combination and report
completion rate, unresolved findings, elapsed time and observed resource use.
The small fixture must meet all its mandatory checks on every accepted result;
failure must remain a failure. This does not promise equal quality on arbitrary
tasks or identical generated code.

**Conclusion:** Codex doing planning and coding is compatible with Temari's design.
The immediate gap is a consistent, useful journey from the chosen entry point to
the intended product outcome. Align policy and completion first, prove the preferred
Archon-managed journey with the existing workers, and then demonstrate provider
substitution against that same contract. Keep additional platform work tied to a
real product requirement.
