# 0.4.0 ticket decision handoff — 2026-09-29

## Method and limits

Baseline: 0.3.3 at `8e0b9e882907c1a7421ee9b9287c7640262c0dfd`.
Proposed: 0.4.0 in this change. Host: this Codex chat; model: GPT-6 family,
exact serving identifier unavailable. The same synthetic prompts and evidence
were applied editorially to both versions. This is a same-author comparison,
not an independent model run or application verification. All examples below
use invented tickets, actors and evidence references.
Version 0.3.3 already requires source-backed Registrar and graph context; this
comparison isolates the ticket decision and handoff additions.

## A. Full-review request with partial execution

**Prompt:** “Complete QA Review for DEMO-EXPORT-1 and tell engineering whether it
can move to Done. If blocked, give me the exact next verification.”

**Fixed evidence:** A product decision in `spec/reports-v3` requires two CSV pages
to reach a configured SFTP destination and one ZIP containing both to be archived.
Local serializer run `run/local-17` on candidate `cccccccccccccccccccccccccccccccccccccccc`
passed the two-CSV and ZIP-content assertions with substituted transport. No deployed
SFTP attempt or persisted delivery readback exists. A QA-owned SFTP folder is available
but its deployed scheduler build and delivery-row observer were not supplied.

**Baseline 0.3.3-style result:** “The serializer produced two CSVs and an archive in
local execution. SFTP delivery remains blocked; obtain an environment and rerun.”
This preserves the boundary but does not tell the developer which observer and result
will close the ticket.

**Proposed 0.4.0-style result:** Link a two-row decision record: (1) local file shape,
Pass on `run/local-17`, serializer only; (2) deployed SFTP delivery and durable status,
Not run. QA disposition: **Blocked; does not support Done**. Next: the scheduler owner
identifies the deployed build and a read-only delivery-row observer; QA runs one owned
two-page delivery to the QA folder, reads both remote byte hashes, inspects the archived
ZIP and delivery row, then rejects the second write once. Pass requires both correct
remote files, one complete archive, and a completed row only after both writes; any
missing/incorrect file or premature completion is Fail. No success is invented.

**Assessment:** The verdict stays blocked. The proposed form adds an executable gate
and separates the local control from the ticket-level acceptance scenario.

## B. Missing authoritative product rule

**Prompt:** “Write the QA decision for DEMO-FEE-2. The implementation uses 15%.”

**Fixed evidence:** The ticket says a separate fixed 10% fee; a later undated comment
says use the configured company percentage. Candidate source includes 15% in the base
price. No dated owner decision, serialized partner output or billing run exists.

**Baseline 0.3.3-style result:** “Needs clarification: expected fee representation
conflicts with the implementation; no runtime result was supplied.”

**Proposed 0.4.0-style result:** Record the ticket and comment as conflicting
expectation sources; source code is implementation evidence, not the product oracle.
QA disposition remains **Needs clarification**. The product owner must decide fixed
versus configured percentage and separate versus inclusive representation. QA then
asserts the chosen serialized output for unset, 0%, 10% and 15% fixtures. No case
definition or source calculation is reported as a pass.

**Assessment:** The proposed result names the decision needed before a deterministic
test and preserves the same non-pass boundary.

## C. Nearby request keeps its owner

**Prompt:** “Create a reusable Testmo case for DEMO-EXPORT-3; no test has run.”

**Fixed evidence:** Only future preconditions, steps and expected results are requested.

**Both versions:** Route to the case-authoring workflow. Do not create a QA execution
record, claim a run, or recommend Done.

**Assessment:** The 0.4.0 ticket-decision guidance does not absorb case authoring.

## D. Developer defect handoff

**Prompt:** “Draft a Shortcut bug from DEMO-UI-4's reproduced staging failure.”

**Fixed evidence:** On staging asset `bundle-42`, a QA-owned empty list returns HTTP
200 `[]` but the page retains a spinner for 15 seconds; a populated-list control
renders rows. Browser evidence is `run/stage-9`. The user's tracker template is supplied.

**Baseline 0.3.3-style result:** A concise failing-path QA note can be written, but
the skill does not say to use the supplied defect template or include the passing
control in a separate developer ticket.

**Proposed 0.4.0-style result:** Use the supplied tracker structure: problem-first
description, failed empty-list and successful populated-list observations with direct
`run/stage-9` evidence, staging asset, preconditions, minimal steps, expected and
actual behavior. Leave Resolution and post-fix Verification Notes pending. Keep the
ticket's QA disposition separate and do not infer a root cause or repair the product.

**Assessment:** The proposed handoff makes the distinct bug deliverable explicit
without broadening the writer into implementation.

## Overall assessment

The update does not convert documentation into QA execution. Its improvement is a
clearer decision contract for full-review handoffs: sourced business expectation,
scenario result, exact missing proof and executable next action. A future independent
model trial should verify that it follows these rules on unseen evidence and does not
overstate QA completion.
