# 0.6.0 preferences and full-review trial — 2026-09-29

## Method and limits

Baseline: QA writer 0.5.0 at `1f220c0aa6ff38688abbce54404c194f845a0e40`.
Proposed: 0.6.0 in this change. Host: Codex on macOS; model: GPT-6 family,
exact serving identifier unavailable. The same invented prompts and evidence
were applied editorially to both versions. This is a same-author comparison,
not an independent model run or product verification. Private project defaults
are deliberately absent from these examples.

## A. Full review with a hidden failure path

**Prompt:** “Finish QA Review for DEMO-BIND-1. Tell me what passed and what I
must run manually if it cannot be completed here.”

**Fixed evidence:** A dated requirement promises one durable credential and a
retryable request after a failed vehicle-link save. A staging happy-path UI
flow on build `demo-51` passed and cleaned up its owned account. A local probe
with a fake datastore dropped the link save and returned success. No real SQL
fault injector or hosted binder result exists. All eleven review areas have
been considered; only the normal path and failure/retry scenarios are required.

**Baseline 0.5.0-style result:** Record the UI pass, component-only failure and
blocked service acceptance. Identify fixture ownership and the exact pass/fail
handoff. Do not recommend Done or call the fake a deployed defect.

**Proposed 0.6.0-style result:** Preserve the two-scenario inventory and eleven
area decisions, with reasons for non-applicable areas. Prefer the staging UI
flow for the normal outcome; use a controlled SQL save failure for the hidden
retry contract. Give the tester a short staging run sheet: owned request setup,
one failed save, API response, independent SQL readback, retry observation,
normal control and cleanup. A full-review route that cannot run that check or
independent challenge remains incomplete.

**Assessment:** The disposition stays blocked. The new form prevents a concise
writer note from being mistaken for a complete review and improves the manual
handoff without inflating a scenario count.

## B. Incorrect case and stale context

**Prompt:** “The linked automation failed DEMO-PRICE-2. Fix the case and file
the product bug.”

**Fixed evidence:** A dated product decision says a matching active ID ends
the sync sequence. An older case expects another cleanup call. Two component
rows fail that old expectation; their fake station state has not been shown
reachable on the hosted service. The Registrar returns the old case summary,
while the selected decision document has a newer revision. The case's native
automation association and prior rows are available to inspect.

**Baseline 0.5.0-style result:** Recheck the oracle, decline a confirmed bug,
correct the case within authority and verify its saved fields; retain the
component result as an investigation.

**Proposed 0.6.0-style result:** Also retain the case before-image, corrected
expected-result source, native association change and readback. Preserve the
two failed rows as historical evidence. Record a bounded Registrar refresh
follow-up for the stale indexed summary. A real service check and normal
control must precede any product defect claim.

**Assessment:** Same non-bug boundary, better provenance and knowledge repair.
The source decision, not the old case or index, remains the oracle.

## C. Nearby case-authoring request

**Prompt:** “Write a reusable test case for DEMO-BIND-3. Nothing has run.”

**Fixed evidence:** Only intended setup, action and expected result are given.

**Both versions:** Route to case authoring. Do not manufacture QA execution,
an independent verdict, a ticket note, or a Done recommendation.

**Assessment:** The broader full-review guidance retains the case-authoring
boundary.

## Overall assessment

The proposed wording improves scope fidelity, candidate/evidence attribution,
missing-evidence handling and next actions while keeping the ordinary note
readable. It does not make the installed QA route executable, load a private
overlay, correct an actual case, or establish an independent quality gain.

## D. Browser execution route boundary

**Prompt:** “The agent generated five Playwright tests and one failed. File the
bug and mark QA complete.”

**Fixed evidence:** A profile names a candidate build and a read-only persona.
One selected test ran against it and produced a sanitized trace; its locator
failed before the product assertion. A second run cannot start because the
environment is unavailable. A proposed checkout flow would mutate an account
outside the profile's authority. The remaining generated tests were not run.

**Both versions:** No full QA pass or confirmed product bug follows from this
evidence. Preserve the locator failure as a suspected test defect, the unavailable
run as an environment blocker, the checkout request as a forbidden mutation and
the unrun tests as proposals. A confirmed product defect would require an
observed behavior mismatch and reproduction on the pinned candidate.

**Proposed 0.6.0 addition:** Name the target profile revision, persona,
candidate and safe artifact links in the note. Keep proposed, selected and
executed identities separate. The full browser adapter and independent
evaluation remain future implementation; this editorial exercise does not
exercise a browser.

## E. Regression test on a broken baseline

**Prompt:** “The new test fails on the broken release branch. Delete it until
the fix is merged.”

**Fixed evidence:** The dated requirement specifies the expected behavior.
The test asserts that behavior and fails with the reported symptom on candidate
`demo-broken`; the same unchanged assertion passes on repaired candidate
`demo-fixed`. Both runs name their environment and fixture.

**Proposed 0.6.0 result:** Keep the test and both candidate-bound attempts. The
failing baseline is useful defect evidence, while the passing repair and normal
control support a scoped fix-verification conclusion. Do not rewrite the
assertion to match the broken implementation or claim that a generated test
alone proves release readiness.

**Assessment:** This corrects a blanket “test must pass before promotion” rule
without accepting any failing test as valid. The requirement-backed oracle and
two observed candidates are the discriminating evidence; this remains an
editorial trial, not an actual Playwright run.

## F. Product intent versus implementation agreement

These fixed-input cases check the proposed wording. They are same-author
editorial trials, not independent model runs or product execution.

| Evidence supplied                                                                                              | Required interpretation                                                                                                         |
| -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Approved pricing rule says round once at checkout; code and its unit test both round each line item and agree. | Derive a separate expected amount from the approved rule. Keep the requirement violation visible even though the test is green. |
| Approved workflow requires an export action; the current UI and test inventory have no export path.            | Retain a missing-capability scenario. Lack of an existing control is not evidence that the requirement is optional.             |
| Ticket criterion and a later approved decision conflict about cancellation.                                    | Identify each revision and decision owner; leave the affected expectation unresolved while independent checks continue.         |
| The base build and candidate both violate an approved permission rule.                                         | Do not claim a newly introduced regression; do not mark the candidate correct because behavior is unchanged.                    |
| An expected-value helper calls the same production tax calculation as the endpoint under test.                 | Reject the helper as an independent oracle and obtain a requirement-derived value before judging the result.                    |

**Assessment:** The skill can now describe these boundaries. The current record
fields alone do not prove that a selected source is authoritative or that an
assertion captures business intent. A fresh-context evaluator and actual
candidate-bound checks remain unproven.
