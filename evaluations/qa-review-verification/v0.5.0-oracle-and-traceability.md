## Method and limits

Baseline: 0.4.0 at `49bb02b0a17c42be24bcd594feb4d466075a0006`.
Proposed: 0.5.0 in `codex/qa-workflow-fidelity` (final revision recorded by Git).
Host: Codex on macOS; model: GPT-6 family, exact serving identifier unavailable.

`767b4bc13016efe1f27c480b5f00c90d65a21f651cfb82e3edcf2aae2675f2af`.

These are same-author, fixed-input editorial trials against the two skill versions.
No independent evaluator or application execution occurred. All examples, tickets,
fixtures and links below are synthetic.

## A. Normal passing scenario

**Prompt:** “Complete QA Review for DEMO-CSV-1 and recommend whether it can move to Done.”

**Fixed evidence:** The dated product decision requires a two-row CSV and one durable
delivery record. Case DEMO-C-17 is approved and its saved revision matches that rule.
Automation `csv-delivery/7` is natively linked. A deployed run on build `demo-41`
asserted both rows and the durable record; independent readback and cleanup passed.
The normal one-row control passed. No other required scenario exists.

**Baseline 0.4.0 result:** A scenario row can cite the decision, case, run, candidate,
readback and control and recommend a scoped pass. It need not show the ticket identity
as a separate matrix field or explicitly sequence case readback before automation.

**Proposed 0.5.0 result:** Record the input/action/outcome example, then one row with
ticket DEMO-CSV-1, case DEMO-C-17 revision, automation `csv-delivery/7`, deployed
run and asserted subset. The reviewer sees the draft note before it is posted; Done
follows only after that review and the agreed tracker workflow. The QA result is still
a scoped pass on `demo-41`.

**Assessment:** Better ticket-to-run traceability and handoff order; no change to
candidate identity or claimed execution boundary.

## B. A suspect failure with an incorrect oracle

**Prompt:** “Create a bug for DEMO-PRICE-2 because the component test failed.”

**Fixed evidence:** An old case expects a cleanup call after an active ID matches.
The current dated ticket rule explicitly ends synchronization on a matching ID.
The component test injects a station response that has not been shown reachable in
the real service. There is no deployed run or normal control.

**Baseline 0.4.0 result:** The source conflict can be marked Needs clarification or
the component result can be labeled at its boundary; a bug draft is possible if the
author mistakes the old case for the governing rule.

**Proposed 0.5.0 result:** Do not call this a confirmed product failure. Compare the
case with the dated ticket rule, flag the case correction and native association for
readback, and mark the injected state investigation pending. Specify the real service
check and control needed before any product bug is filed.

**Assessment:** Reduces a concrete false-positive path. No claim that the real service
passes; the unverified scenario remains open.

## C. Missing fixture and execution

**Prompt:** “Finish QA Review for DEMO-PAIR-3; the local binder probe failed.”

**Fixed evidence:** A fake store drops a pairing save. The component method reports
success, but there is no SQL or hosted API result. A QA-owned account exists; a safe
station and fault injector do not. The expected retry behavior is in a dated epic.

**Baseline 0.4.0 result:** A component failure and blocked hosted acceptance row,
with an exact missing fixture and pass/fail check. The ticket is not ready for Done.

**Proposed 0.5.0 result:** Keep the component finding at its actual boundary and
explicitly check whether the injected save failure is reachable with real SQL. Link
the epic example, case revision and test identity in the ticket matrix. Name the
station and fault injector owners, independent SQL readback, normal control, cleanup
and the exact success/failure observations. No confirmed service defect is claimed.

**Assessment:** Same blocked disposition, clearer defect confidence and test plan.

## D. Nearby case-authoring request

**Prompt:** “Draft a reusable case for DEMO-PAIR-4; no test has run.”

**Fixed evidence:** Only the future setup, action and expected outcome are supplied.

**Both versions:** Route to case authoring. Do not claim an execution, make a QA

**Assessment:** The new QA closeout guidance does not absorb case authoring.

## Overall assessment

The 0.5.0 instructions retain the 0.4.0 evidence boundaries and improve oracle
checking, case readback, ticket linkage and the note-review handoff. The record
validator additionally rejects a Passed scenario whose only implemented binding is
a case definition or a gap. These editorial trials do not establish model compliance;
an independent trial and real-ticket replay remain future verification.
