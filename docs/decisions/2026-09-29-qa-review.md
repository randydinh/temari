# QA Review decisions — 2026-09-29

These decisions refine the existing QA domain design. They apply to the shared
Temari contract; employer-specific defaults and templates remain external
overlays. A writing skill, a test case, a green command, and a workflow receipt
each have narrower meanings than a full product QA disposition.

## D-2026-09-29-01: Establish the oracle before automation

Status: accepted

For new functionality, derive input, action and observable-outcome examples from
the ticket, epic, specification and dated product decisions during QA Review or
earlier. Compare them with existing expected behavior. A conflict pauses the
affected case and automation work until a product owner resolves the rule.
Implementation source, current UI behavior, an older build, prior QA prose and
a test's current assertion are observations, not independent expected-behavior
authority. They cannot silently become or revise the requirement.

## D-2026-09-29-02: Use context providers within admitted scope

Status: accepted

A project may require a Content Registrar and codebase graph lookup for each
task. Queries and source reads occur after policy and source-scope admission.
Retain selected revisions, graph freshness and direct code checks in a small
reusable context packet. Record missing or stale context and an authorized
maintenance follow-up. Providers guide discovery; they do not decide the QA
oracle, grant authority or set the disposition. This preserves the selected
core/overlay boundary in `docs/decisions/2026-09-18.md`.

## D-2026-09-29-03: A full review needs scenario evidence

Status: accepted

The same review contract applies across teams. A full review maintains a stable
inventory of distinct required scenarios and records applicability across all
eleven canonical areas. Scenario count is not a quota. Each required scenario
retains the expectation source, candidate and fixture, exact attempted check,
observed result, evidence and unresolved work. A ticket's Done or approval
state does not prove the review. An evidence-only note remains a partial
deliverable when execution or independent evaluation is required.

## D-2026-09-29-04: Separate case, automation and result identities

Status: accepted

When a project uses a test-management system, settle the example, reconcile
the case definition, verify an authorized saved change by readback, then link
automation that actually asserts the behavior. The scenario matrix records
ticket, case revision, automation identity and actual run/result separately.
Retain skipped and failed rows. Correct a bad expected result or native mapping
with a before-image and readback; preserve old runs as historical evidence.
Neither case existence nor a native association establishes ticket acceptance.

## D-2026-09-29-05: Minimize false product defects

Status: accepted

Check the governing rule, test oracle, fixture realism, candidate, normal
control and observation boundary before reporting a bug. Distinguish reported,
source-supported, substituted component, integration and deployed findings.
A blocked fixture or unresolved product rule is not a product failure. Prefer a
functional user-facing check when it can prove the outcome; use service, SQL,
queue, simulator or controlled fault checks for hidden effects. A suitable
nonproduction runtime can prove those boundaries. A base branch without the
feature cannot be cited as evidence of a regression in that feature.

## D-2026-09-29-06: Keep writing, review and state changes separate

Status: accepted

The QA note summarizes behavior and evidence for the named scope, with an
executable pass/fail handoff for every blocked required scenario. Project or
user review gates apply before posting or changing tracker state. A defect
report follows the user's established template and avoids unsupported cause
claims; reporting a defect does not itself authorize product repair. External
writes require their own authority, before-image and readback.

## D-2026-09-29-07: Keep private preferences outside shared source

Status: accepted

The public skill and domain model carry reusable rules. Personal or employer
application maps, reviewer defaults, exact tracker templates, fixture aliases
and account bindings stay in an external overlay. The source checkout may read
a private host preference file through `AGENTS.md`; a distributable artifact must
validate and load an approved overlay separately. An overlay cannot add engine
stages or grant authority.

## D-2026-09-29-08: Admit browser execution through the QA record

Status: accepted as a delivery direction; execution is not yet implemented

Adapt the useful ticket-driven browser workflow from the reviewed QA-agent
resources as scoped Temari capabilities, without installing a third-party skill
catalog wholesale. Bind an approved target profile to the assignment: candidate
and environment, persona, safe-mutation authority, owned test data, auth-state
handling and evidence redaction. Map requirement-linked proposed scenarios
separately from selected coverage and actual attempts. A browser attempt needs
assertions, observations and safe artifact references; triage a failure as an
application defect, test defect, environment issue or unresolved. Promote a
suspected application defect only after reproduction and review. Feed verified
attempts into the canonical `QaReviewRecord`. A permanent regression test may
first fail on a broken baseline; its oracle must come from the requirement,
and the same assertion should pass on the repaired candidate when available.
External tracker or test-management writes need reviewable payloads,
specific authority and saved-state readback. Candidate binding and an
independent evaluator remain required for a full disposition.
The browser capabilities are a first increment, not a complete QA-task catalog.
Select a task playbook and load a focused skill only when its step needs it.

## D-2026-09-29-09: One QA domain with standalone and Poteto entry points

Status: accepted as a design requirement; host execution remains blocked

Use the same QA domain capability and canonical workflow engine for a standalone
ticket or release assignment and for QA verification called from a Poteto
engineering run. Poteto owns the engineering build or repair and consumes the
QA disposition at its verification gate; QA owns scenario evidence and the
product-facing disposition. A Poteto call binds the parent run, candidate
revision or deployed build, requirement revisions, environment, scope and
allowed actions. A required scenario that is Failed, BlockedOrIncomplete or
NotRun keeps the QA gate unresolved. A procedural receipt or drafted note cannot
turn it into a pass. A low-risk engineering route may use a proportionate direct
check when a full QA assignment is not required.

QA may request bounded test implementation or defect repair through Poteto.
That callback carries the existing `parentReviewId` recursion guard. A repair
creates a new candidate; QA then rechecks affected scenarios on the new
candidate. The QA evaluator stays fresh-context and independent of the QA
record author. Do not fork a second QA lifecycle or a Poteto-only QA record.

## D-2026-09-29-10: Compose QA with task playbooks and focused skills

Status: accepted as an architecture direction; playbooks and adapters are not
yet implemented

Within the one QA domain, route the assignment to a task playbook. Its steps
load reusable skills only when needed, use an admitted project control/profile
adapter, and retain results in canonical candidate-bound evidence. This follows
the P-stack structure without making every QA task use one browser workflow.
Triage, duplicate checks, ownership, reproduction, verify-existing-fix and
before/after evidence are candidate playbook patterns from the resource review;
case design, API or service checks, and release review need their own applicable
steps. Apply a UI reproduction or video requirement only when it proves the
selected task's behavior. Poteto owns bounded engineering repairs and returns a
new candidate for QA recheck.

The legacy Benny references describe a Cursor automation dependency, not a
current public Temari QA route. Reuse useful triage and evidence patterns only
after source review. Treat Slack triggers or communication automation as a
separately authorized host adapter using the existing scheduler and store,
without adding another lifecycle. The source-by-source adoption matrix and
proposed playbook catalog refine selection and skill boundaries; neither admits
an executable QA route. `docs/qa-playbook-design.md` records the proposed task
families, selective loading contract, schema gaps and distinguishing eval cases.
Keep third-party skill text outside the public bundle unless its license and
provenance allow distribution; independently author Temari's task contracts.

## D-2026-09-29-11: Product intent determines correctness

Status: accepted; semantic enforcement and executable evaluation remain open

Every QA task carries a bounded, revisioned expected-behavior baseline from
applicable product decisions, requirements or domain rules. Record its authority,
affected actor and business outcome, preconditions, permissions, state and data
invariants, observable success and failure, and conflicts or assumptions with
their decision owner. Identify the approved authority for this scope and any
superseding decision; do not impose one universal document ranking. Ambiguous
rules stay unresolved while independent checks proceed.

Derive initial scenarios from intended outcomes, including a required capability
missing entirely from the implementation; then add risks found in code and
architecture. Choose unit, property, API, integration, UI or exploratory checks
according to the claim. Derive expected values independently of the code under
test: two surfaces or a test helper can agree with production while sharing the
same business-rule error. An old build that already violated the requirement is
not a successful baseline. A supported violation may be reported without proving
it was introduced by the latest change; distinguish that from a regression
claim. Classify behavior as intentional or a feature request only with product
intent support.

Poteto repairs against the same expectation and returns a new candidate; repair
cannot redefine success. The independent QA evaluator receives the pinned intent
baseline, uncertainty and candidate evidence and checks whether assertions
establish the business outcome. Existing `QaReviewRecord` fields such as
`requirementRefs`, `sourceRevision`, `expectedBehavior` and `behavioralReason`
support traceability but do not prove source authority or semantic correctness.

test inventory and authorized nonproduction environment. A quality evaluation
should include a known pass, known application defect, broken test, unavailable
environment and forbidden mutation, and compare false findings and omissions
against the current process.
