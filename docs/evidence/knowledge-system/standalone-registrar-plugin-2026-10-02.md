# Standalone Content Registrar plugin artifact, 2026-10-02

The user confirmed that a recipient needs to install and use the Knowledge workflow, not independently develop its source. Keep development in the Temari Nx monorepo and project an independently identifiable plugin artifact. A full Temari public package would expose unrelated workflow skills and host entrypoints. A bundled single-file Knowledge CLI would change source-relative Python helper and provenance paths, so this first release candidate retains the verified canonical runtime closure. The standalone artifact contains one Knowledge skill, one launcher, the pinned Registrar payload, that runtime closure, and its own `.codex-plugin/plugin.json` and checked manifest. It omits Temari's other public skills, policy, host entrypoints and QA tools. The runtime closure still contains shared Temari libraries; the artifact is smaller in user-facing capability, not a claim of source isolation from every shared library.

`pnpm nx run workflow-runtime:knowledge-plugin-package --args='--output /absolute/new/artifact'` builds an exclusive directory. `tools/knowledge-plugin.mjs check --artifact /absolute/artifact --expected-manifest-sha256 HEX` verifies the exact file inventory, standalone identity, executable launcher, pinned Registrar source and nested canonical runtime against an externally recorded SHA256 of `knowledge-plugin-manifest.json`. Neither operation reads a TypeSafe key. The artifact is made from a separately verified public package and records its source revision, dirty bit, parent manifest digest and hashes of the three additional plugin-specific source files. It rejects symlinked source files and parent components; the delivered artifact checker rejects symlinks throughout. Do not distribute a dirty build. The plugin metadata intentionally omits a separate license claim while the Registrar distribution terms are unresolved.

The relocated macOS test builds the artifact, verifies tamper and symlink rejection, installs the pinned Registrar into an external home, registers a synthetic source, marks it `local-only`, runs `journey-intake` and BM25 `journey-search`, checks one verified cited result and zero Jev requests, then disables and replaces the plugin directory while the external disabled selection persists. The temporary source contains one synthetic text file. No real user corpus, Keychain credential or hosted call is used. The existing bundled Temari Knowledge skill remains present for migration, and both launchers share the same external home and `temari-content-registrar` MCP name; operators must avoid connecting two competing homes under that fixed name.

An isolated Codex CLI 0.154.0 local marketplace accepted the projected plugin, listed it as enabled, and launched its cached Knowledge entrypoint. After setup and `disable`, CLI remove/reinstall retained the external `disabled` selection and installed Registrar. The final clean artifact pins reviewed commit `dd02e27f1911a1dc7aa993b9098ea68a5be0250f` with `dirty:false`; its manifest SHA256 is `144e7519db02e9820f899182bf2eb4df50069b2c35552627892c8250c8d1a2ed`. The checker passed the source artifact and Codex's cached copy. [PR #198](https://github.com/randydinh/temari/pull/198) merged at `f94747d0d5c6fd31494e81024578cc9c504577b4`, with the reviewed and merged trees equal. It did not exercise the desktop Plugins Directory. [OpenAI's local marketplace guidance](https://developers.openai.com/plugins/build/plugins) describes the recipient-side marketplace source and install path.

This is a **package, relocated launcher and isolated CLI install proof**, not a published release, external-provider swap, full retention/purge implementation, desktop UI installation, or Windows proof. Source license and upstream/downstream reconciliation remain required before public distribution. A recipient of a private artifact can use the local package without Temari repository access, but still needs supported local Python tooling and their own TypeSafe credential if hosted Jev is enabled for registered sources. The default Knowledge selection is Registrar; explicit local-only sources do not call Jev.
