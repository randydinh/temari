# Actual Registrar BM25 scale diagnostic (2026-10-02)

**Standing:** Local synthetic performance baseline only. This does not establish
answer quality, a production service-level objective, or a reason to change the
default ranker.

## Hypothesis and setup

`source_archive.py` selects and verifies archived text, then builds a new
in-memory SQLite FTS5 table for each BM25 discovery. We expected end-to-end
discovery cost to rise as the selected archived text grew. The opt-in
[`bench-archive-bm25.py`](../../../tools/bench-archive-bm25.py) runner creates
three deterministic plain-text sources with 100, 400, and 500 files, marks each
`local-only`, and captures them through the actual Registrar CLI. Its cumulative
discovery scopes contain 100, 500, and 1,000 documents across one, two, and
three sources. Every captured file had a retained original and text
representation; the runner checked each original SHA-256 against its generated
bytes using pinned archive inspection.

The runner uses the same two-term synthetic query at each size. Only one
document contains both terms. Every measured discovery starts a **fresh CLI
process** against the pinned generations, with `--mode bm25 --limit 3
--max-bytes 16000`. It independently reads the top archived document after
each response and checks source, generation, manifest, original and
representation hashes against the BM25 top row in both the read response and
its citation. It also checks the zero-based Unicode code-point span against
the exact quote and body, then checks the query terms. The citation read is
outside the timer. It requires one nonempty selected-index digest to remain
identical throughout each size's repeated discoveries. The runner makes one
warmup discovery and seven measured
discoveries per size. `time.perf_counter_ns` brackets only the discovery CLI
invocation, so process startup and archive validation contribute to these
end-to-end observations; source creation, capture, archive inspection, and
citation readback do not. P95 uses nearest rank. With seven samples, it is the
largest sample, so it should not be interpreted as a stable tail estimate.

The host was Darwin 25.5.0, arm64, with 18 logical CPUs. Registrar ran under
Python 3.12.13 and SQLite 3.53.1 with FTS5. Its `source_archive.py` SHA-256 was
`bd12ded293c2e7f99d9a8b82a0666181f28e2ebfbcb00c6173786233b47f910f`.
Capture limits were 1,000 entries per source, 8,192 bytes per file and text
representation, and 8 MiB total original bytes per source. The retained
private run report SHA-256 is
`29126f569daf018d0c34b043b96989231523bd3a98347a6116b283e9cd0edc04`.
The runner's output is outside the repo; it creates synthetic source roots in
the host's system temporary directory.

## Observations

| 100 | 1 | 55,766 | 128.515, 127.095, 127.216, 126.757, 127.425, 129.107, 128.870 | 127.425 | 129.107 |
| 500 | 2 | 278,566 | 674.498, 674.979, 710.128, 673.035, 689.495, 676.236, 642.756 | 674.979 | 710.128 |
| 1,000 | 3 | 557,066 | 1460.978, 1442.576, 1451.945, 1504.124, 1463.777, 1586.319, 1581.199 | 1463.777 | 1586.319 |

All 24 discovery responses, including warmups, passed independent pinned
top-citation readback. The actual CLI also refused a query with 33 distinct
terms under its 32-term BM25 limit. The runner clears `TYPESAFE_API_KEY` in
each Registrar subprocess and uses no hosted-model or keychain path.

The observed median increased with the selected scope on this host and fixture.
The measurement includes both archived-selection validation and fresh FTS5
construction, so it does not isolate the index-build portion. Source count also
increased with document count. A persistent index or cache remains an
unmeasured design option; these results do not justify implementing one yet.

## Reproduction and verification

From a clean Temari checkout with `uv` and Python 3.12 available:

```sh
export BM25_TMP="$(mktemp -d)"
UV_CACHE_DIR="$BM25_TMP/cache" uv venv --python 3.12 "$BM25_TMP/venv"
UV_CACHE_DIR="$BM25_TMP/cache" uv pip install --python "$BM25_TMP/venv/bin/python" -e packages/workflow-runtime/registrar
"$BM25_TMP/venv/bin/python" tools/bench-archive-bm25.py \
  --python "$BM25_TMP/venv/bin/python" --counts 100,500,1000 \
  --warmup 1 --repetitions 7 --output "$BM25_TMP/report.json"
```

The focused actual-CLI smoke used counts 5, 10, 20 and two repetitions; it
passed pinned citation verification and the 33-term refusal. The full
100/500/1,000 run also passed on the final citation-checking script. The script is deliberately outside normal Nx
integration: its 1,000 source extractions and repeated index rebuilds are too
costly for a routine test. There is no timing threshold in CI.

Verification on the candidate worktree:

- `pnpm nx run knowledge:typecheck --skipNxCache`: passed.
- `pnpm nx run knowledge:integration` with `TEMARI_REGISTRAR_SOURCE` set to the
  bundled Registrar and `TEMARI_REGISTRAR_PYTHON` set to the temporary Python
  environment: passed 96/96 actual-CLI cases.
- `pnpm nx run knowledge:test --skipNxCache`: passed 43/43.
- `pnpm nx sync:check`: passed, workspace up to date.

These Nx checks preceded the final citation-assertion-only runner edit; the
focused and full actual-CLI benchmarks above were rerun after that edit.

The fixture uses small plain-text records and a rare literal marker, so it does
not measure mixed media, paraphrase recall, no-answer calibration, realistic
knowledge-worker tasks, concurrent load, or the 10,000-document/64 MiB index
caps. The fixture is ASCII, so its code-point span check does not test
multi-byte Unicode text. It tests only the 32-term refusal. The five broader
Knowledge finish predicates in the current handoff remain open.
