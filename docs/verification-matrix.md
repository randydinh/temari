# Temari verification matrix

This matrix is the working answer to one question: **what evidence would show
that the Temari workflow platform is being built correctly?**

It separates four things that are easy to confuse:

1. The design claim is coherent.
2. The implementation exists.
3. A test or journey proves the behavior.
4. A durable artifact proves what happened for a particular revision.

An entry is not complete because its source file exists or because a typecheck
passes. A row reaches Proven locally only when the named proof is runnable and
the result is retained or reported. A row marked Partial, Planned, or Gated
must not be used as evidence for a stronger completion claim.

## Status vocabulary

| Status         | Meaning                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------ |
| Proven locally | Current code and a repeatable local test or check cover the claim.                               |
| Partial        | A bounded, deterministic, fixture, or source-specific path is proven, but the full claim is not. |
| Planned        | The design names the boundary, but the current Nx implementation does not provide it.            |
| Gated          | The behavior exists or has a proof path, but release or cutover acceptance is still outstanding. |
| Unknown        | The repository does not yet contain enough evidence to make a responsible claim.                 |

## Minimum acceptance bar

Before calling the Nx platform “built correctly,” require at least these rows
to be Proven locally or backed by an explicitly accepted release gate:

- ARC-02, PLAN-01, PLAN-02, and HOST-01.
- PAR-01 for local parallel worker routes; PAR-02 remains a release gate for
  unattended parallel or failover routes.
- KNOW-01, KNOW-02, and KNOW-03 for any knowledge-backed route.
- VERIFY-01 and VERIFY-02.
- PROV-01 and PROV-02 for any unattended or delegated route.
- SEC-01 and SEC-02 before using customer, employer, or authenticated data.
- CUT-01 before retiring the legacy installation.

Rows marked Partial are acceptable for a local foundation only when the missing
scope is named in the run report. They are not evidence for a complete
production platform.

## How to use this matrix for each change

1. Add or update a row before implementing a cross-cutting behavior.
2. Name the exact source file or design decision that creates the requirement.
3. Add both a success proof and a failure proof. Failure paths are part of the
   contract for a system that promises honest blocking and resumability.
4. Run the smallest direct check first, then the relevant user journey.
5. Retain the command, revision, exit code, and artifact paths.
6. Update the status only from observed evidence. Do not promote Partial to
   Proven locally because the code looks complete.
7. Re-run rows whose evidence is revision-bound after a restack, package rebuild,
   provider change, or host change.

## Baseline commands

From the Nx workspace:

```sh
pnpm exec nx run-many -t typecheck test --parallel=1
pnpm exec nx test temari-core
pnpm exec nx test workflow-engine
pnpm exec nx test host-adapters
pnpm exec nx test knowledge
pnpm exec nx run knowledge:integration
```

closeout.

## Known gaps at this revision

The matrix intentionally leaves these as incomplete or gated:

- Cancellation policy and durable notifications beyond the current
  lease/event/run-status/stage-checkpoint slice.
- Live proof for broad host capability declarations.
- Full live Archon model execution and cryptographic actor identity.
- Public package installation and drift checks for the Nx surface.
- Executor-integrated provider-specific log capture in the Nx runtime; the
  provider-neutral callback publication boundary and local child/serial-stage
  workspace manifests are proven only when their explicit bindings are
  supplied.
- Cutover and rollback evidence strong enough to retire v4.1.
